03 / 19Situation/The demo
Situation

End of 2022: two research models,
and three weeks to prove them.

  • Adobe Research had two foundational models — text-to-image and text effects. No product around them.
  • Another engineer and I were asked to build the UI platform to showcase both for an upcoming Adobe event in February.
  • Hard deadline: 3 weeks. Leadership deeply involved — this was a company-visibility moment, not a side project.

05 / 19Action/v1 · the sprint

Ship fast: a single React SPA

07 / 19Result/Inflection
Result — and the architectural debt it exposed

Shipped on schedule.
Then demand broke the monolith.

Both models shipped for the event. Internally the pull was immediate: teams across Adobe wanted their own research on the surface. The single bundle that made v1 fast now made scale impossible.

Coupling in the single bundle

  • One shared release train — every team's work gated on one deploy
  • Our merge queue became the org's bottleneck
  • No fault isolation — one module's bug shipped to all

What the org actually needed

  • Independent ownership, repos, and release cadence per team
  • Platform services without platform coupling
  • Us out of the critical path for every new model
08 / 19Trade-off/The framework call
Key trade-off #1

React got us live in 3 weeks —
and became our org-wide friction.

What it bought us

  • Fastest path to a credible UI on a hard deadline
  • Deep team familiarity — no ramp cost when speed mattered most
  • Rich Spectrum component ecosystem out of the box

What it cost us

  • Many Adobe teams didn't work in React — adoption drag
  • Forced a shell architecture so teams could live outside our monorepo
  • A decision made for week-3 speed shaped the platform for two years

I'd still choose React for the sprint — but I under-weighted org heterogeneity. That lesson drove every architecture decision that followed.

PHASE 02 · 2023

10 / 19Action/Shell architecture
Action — v2 architecture · custom micro-frontend

Invert it: shell as host, modules
as network-loaded Web Components.

  • Shell keeps a registry of module URLs and loads each team's bundle over the network at activation — our own micro-frontend runtime.
  • Every module ships as a Web Component (custom element) — framework-neutral, mounts anywhere.
  • Shell injects platform services through properties & attributes, behind one common services interface.

12 / 19Action/Agnostic platform
Action + trade-off #2 · the interop problem

Framework-agnostic —
even when the shell is React.

Any stack, own repo

  • Teams build in React, Lit, Vue, or vanilla
  • Compile to a custom element, ship a bundle to a URL
  • Own repo, own release cadence — outside our monorepo

The hard part: React ↔ custom elements

  • React doesn't cleanly pass props & events to custom elements
  • We built a home-grown React adapter (ref-based prop/event bridge) to mount Lit/Vue modules
  • Plus a common services interface so every module got auth/analytics identically

"Agnostic" wasn't a slogan, it was an interop layer we had to build. That wrapper tooling is what let other teams actually leave the monorepo without losing platform services.

13 / 19Action/Metadata-driven UI
Action — my signature project

Stop hand-building UI per model.
Render it from typed descriptors.

Each model ships descriptors for its inputs; the engine maps each kind to a control. New model, no new UI code.

// illustrative — typed input descriptorsinputs: [ { id:'prompt', kind:'text' }, { id:'strength', kind:'slider', min:0, max:1, step:.05 }, { id:'reference', kind:'imageRef' }, { id:'style', kind:'select', options:[…] }, ]

Engine renders

  • text→textarea
  • slider→range + numeric
  • imageRef→image drop zone
  • select→style dropdown
2–3 wks → 3–4 days
Time to add a new model to the UI. A ~4× drop in onboarding cost.
Still on today
Powers new model releases and third-party integrations to this day.

17 / 19Reflection/What I learned
Trade-offs & lessons

What I'd carry forward —
and what I'd do differently.

Worked

  • Optimize for speed first, then invert to a platform when demand proved real
  • Turning the shell into a contract removed us as the bottleneck
  • Metadata-driven UI — one abstraction still paying off years later

Would do differently

  • Weigh org heterogeneity earlier — the React call created lasting drag
  • The monorepo split solved adoption but fragmented ownership
  • My recurring tension: innovation vs. tech debt — I'd budget debt paydown deliberately, not reactively

The through-line: at staff level, the architecture is a bet on how the org will grow — not just on the code.
